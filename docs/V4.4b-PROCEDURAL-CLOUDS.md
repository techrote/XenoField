# XENOFIELD V4.4b — Procedural Clouds

V4.4b adds a **dedicated procedural-cloud instrument** alongside the generalized XenoVolume. It renders a real world-space volume into the existing HDR/compositor graph; it is not a detached preview and it does not replace XenoVolume.

## Reference implementation

The cloud density/shading path deliberately preserves the useful behavior and control vocabulary of `jeantimex/procedural-clouds`:

- compute-generated 3D density cache;
- two ping-pong cache generations;
- configurable cache update interval;
- smooth interpolation between cache generations;
- stochastic view-ray entry;
- early transmittance termination;
- the same density/coverage/scale/altitude/detail shaping order;
- the dedicated cloud pass retains the source-style live light march, including Ray Steps, Light Steps, Shadow Dark and Sun Intensity.

The source cloud's visible controls are exposed in the same order: **Density, Coverage, Scale, Altitude, Detail, Wind Speed, Skip Light March, Ray Steps, Light Steps, Shadow Dark, Sun Intensity, Cloud Height, Cache Res, Cache Update, Cache Smooth**.

The procedural helpers are a Xenofield WGSL re-expression of the reference graph rather than a byte-identical copy of Blender's internal noise implementation. Stage order, control semantics, cache behavior and optical controls are preserved. This distinction matters when comparing individual voxels, but the intended end-stop cellular/membrane behavior is retained as a first-class art target.

`joshbrew/webgpu_realtime_clouds` was also studied for its direct-render integration pattern: a cloud renderer owns its output/resources while a world-space box is provided by the host renderer. V4.4b follows that clean ownership model while retaining Xenofield's own SceneAux, depth clipping, HDR and compositor architecture.

## World volume tool

The **CLOUDS** dock entry opens a separate compact panel. The procedural field is evaluated in a stable local domain, then mapped into a user-controlled world-space AABB. World placement therefore does not force the density graph itself to change.

Controls:

- Position X/Y/Z
- Size X/Y/Z
- MOVE / SCALE
- axis constraints: XYZ, X, Y, Z, XY, XZ, YZ
- EDIT IN VIEW
- BOUNDS

With **EDIT IN VIEW** active:

- drag moves or scales the selected axes;
- mouse wheel moves through view depth or scales the selected axes;
- Shift applies fine control;
- the normal camera drag is suppressed while the cloud manipulation owns the pointer.

Clouds depth-clip against SceneAux linear depth. `Depth Softness` fades density before the opaque surface boundary rather than producing a hard cut.

## Resource model

- Two persistent `RGBA16Float` 3D density caches are allocated only while the cloud instrument is enabled.
- Cache resolution is user controlled through 128 in the normal UI, with validated direct-entry headroom to 256.
- The effective cache edge is bounded against the configured texture budget; the requested and actual cache sizes are both exposed in metrics.
- The cloud ray target can run at 1× through 1/8 internal resolution using `Render divider`.
- Disabling the procedural cloud releases its 3D and screen targets and removes Cloud Density / Cloud Raymarch / Cloud Composite work from subsequent frames.

## Pass ownership

```text
SceneAux / linear depth
        ↓
HDR scene
        ↓
Procedural Cloud Density  [multi-rate 3D compute]
        ↓
Procedural Cloud Raymarch [world AABB + scene-depth clip]
        ↓
Cloud Composite           [HDR premultiplied alpha-over]
        ↓
remaining Kinetic compositor / AA / display
```

The dedicated source-style nested light march exists **only** in this explicitly selected procedural-cloud instrument. The generalized XenoVolume retains V4.4a's cached-lighting default.
