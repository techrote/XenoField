# XENOFIELD V4.3a-r1 — Renderer / Standalone Hotfix

## Reported failures

Chrome and Firefox both rejected the projected-mesh WGSL. The first parser failure was a reassignment to an immutable `let w` in the triplanar mapping branch. A second latent instance, `let foamMask` followed by reassignment, was found during the audit and fixed before packaging.

Because V4.3a compiled the mesh shader inside the same hard-fail initialization path as the sky/liquid renderer, that one mesh shader error aborted the complete WebGPU renderer. The app then intentionally showed its CPU SkySynth/environment fallback full-screen, which is why every global preset appeared to be “just SkySynth.”

The black SkySynth panel preview was a related context-ownership problem rather than the environment being rendered into the wrong viewport. The preview canvas had already acquired a WebGPU context before shader validation failed; browsers do not then allow the same canvas to acquire a 2D context for the CPU fallback preview. V4.3a-r1 delays preview WebGPU binding until successful pipeline validation.

The standalone also used a module Blob worker. Under direct `file://` launch this can be rejected as a cross-origin top-level worker script. The standalone worker bundle has no imports, so V4.3a-r1 launches that embedded bundle as a classic Blob worker; normal source/server builds retain the module-worker path.

The Chromium `powerPreference` warning on Windows is benign and unrelated.

## Hardening

The projected-mesh shader and pipeline are now isolated from the core renderer. If a future projection-only shader fails, liquid/field rendering can remain live and metrics expose `meshProjectionReady` / `meshProjectionError`.

## Validation scope

- Node functional tests and static source/WGSL contracts.
- Chromium DOM/component checks.
- Embedded classic worker creation and an actual SkySynth worker frame round-trip.
- Exact `file://` browser navigation could not be exercised in the container because its Chromium policy blocks local-file navigation.
- This environment still exposes no WebGPU adapter, so final GPU shader compilation/rendering must be confirmed on the target Chrome/Firefox installation.
